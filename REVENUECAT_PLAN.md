# RevenueCat integration — plan **and** working prompt

**How to use this file.** Paste the whole thing into Claude Cowork at the start of *every* session on
this work. It is written to be re-read from cold: it carries the repo facts, the invariants, the
phase plan, and a progress ledger the agent keeps up to date, so a fresh agent with zero memory can
open it, see exactly where the work stopped, and continue.

The work is deliberately phased with **STOP gates**. At each gate the agent reports and waits for a
human decision instead of barrelling on. Phase 0 exists because it can invalidate the entire
project, and finding that out after three days of code would be the expensive way to learn it.

---

## 0. Mission

Replace this app's direct StoreKit 2 purchase layer with **RevenueCat**, without losing a single
paying customer, without changing what the player can buy, and without breaking the determinism
guarantee the whole codebase is built around.

This is a **backend swap behind a stable interface**, not a product change. The paywall, the prices,
the free/Pro line, and the grandfathering promise all stay exactly as they are. If a phase starts
changing what the user sees or what they get, it has gone out of scope — stop and ask.

**Why RevenueCat is worth it** (state this honestly, don't oversell): cross-platform entitlements if
Android ever happens, real subscription analytics without building them, server-side receipt
validation, webhooks, price/paywall A-B experiments, and win-back/offer management without an app
update. **What it costs:** a third-party SDK, a revenue share above the free tier, one more
dependency in the purchase path, and — the one that has actual App Store consequences — the end of
this app's "Data Not Collected" privacy declaration. See Phase 6.

## 2. Invariants — break any of these and the work is wrong

These are not style preferences. Each one has a concrete failure behind it.

1. **Nothing in `src/engine/` may ever read an entitlement.** The engine is pure and there is a
   pinned 160-week reproducibility test that runs a seed twice and compares byte-for-byte. Every
   Pro gate sits on a *player action* or a *UI surface*, so a free run and a Pro run are identical.
   If you find yourself importing anything purchase-related into `engine/`, stop.
   **The RevenueCat SDK must never be imported anywhere under `src/engine/`.**

2. **Pro sells content and modes, never an in-run advantage.** No stat boosts, no cheaper parts.
   This is what keeps App Store Guideline 3.1.1 (pay-to-win) off the table.

3. **One purchase surface, forever.** `openPaywall({ reason, onUnlocked })` in
   `src/state/paywall.ts`, rendering `src/components/Paywall.tsx`. Never build a second paywall.
   If RevenueCat's own hosted Paywalls product is proposed, that is a **product decision for the
   user**, not a migration step — raise it at a gate, do not just adopt it.

4. **Grant only on confirmed success; revoke only on a definitive "no".** Cancel, pending, error and
   "SDK unreachable" grant nothing. And critically: a *partial* read — one source throws while
   another says no — is **not** evidence of a lapse. `syncPro()` already encodes this and it must
   survive the migration. Revoking on a partial read logs paying customers out of what they bought.

5. **Never lower `FIRST_FREE_BUILD` (currently `5`).** It is the boundary that grandfathers everyone
   who bought the app for $8.99 before it went free. See Phase 3 — this is the highest-risk phase.

6. **A Pro convenience must never reach a scored mode.** The Time Machine snapshots the freeform
   campaign only, never a scenario or a daily/weekly challenge, because those have stars and seeded
   leaderboards.

7. **Design tokens only** (`src/design/tokens.css`), **Lucide icons only**, no emoji in product UI,
   no real brand names. Popups follow the liquid-glass standard in `CLAUDE.md`.

8. **The kill switch stays.** `NATIVE_PRO_WIRED` in `src/state/proStore.ts` must continue to hide
   every purchase surface when false, so a broken store can be neutralised with a patch release
   rather than leaving dead buttons (an App Review 2.1.0 rejection).

## 3. The current architecture — and the exact seam to swap

This codebase was built with a single, named boundary between the app and the store. **Use it.** The
correct migration writes a RevenueCat adapter that satisfies the existing interface; it does not
spray `Purchases.*` calls through the UI.

```
  UI screens (HQ, Scenarios, Progress, Company, Settings)
        │  isLocked() / eraAdvanceLocked() / scenarioLocked()
        ▼
  src/state/proGates.ts ......... the ONE free⇄Pro table. Must not change.
        │  openPaywall({ reason, onUnlocked })
        ▼
  src/state/paywall.ts .......... routing + first-run timing
  src/components/Paywall.tsx .... the one purchase surface
        │  getProCatalog() / purchasePro() / restorePro() / syncPro() / manageProSubscription()
        ▼
  src/state/proStore.ts ......... store orchestration + entitlement writes   ◄── most change here
        │  storeKit().<method>()
        ▼
  src/state/storeKitBridge.ts ... ★ THE SEAM ★  interface SiliconStoreKitPlugin
        ▼
  ios/App/App/SiliconStoreKit.swift ... StoreKit 2 direct                    ◄── replaced/retired
```

Supporting files:

| File | Role |
|---|---|
| `src/state/pro.ts` | Product catalog, `ProTier`, the persisted `ProRecord`, expiry logic, `FIRST_FREE_BUILD`, `isFoundingBuild()` |
| `src/state/usePro.ts` | `useIsPro()` / `useProStatus()` React hooks |
| `src/state/iap.ts` | **Legacy** standalone Creative Mode non-consumable. Kept wired so past buyers keep it |
| `src/state/entitlements.ts` | The legacy sandbox/Creative entitlement store |
| `src/components/ProNudge.tsx` | Billing-grace-period strip only |
| `src/state/nativeStore.ts` | Mirrors `silicon.pro.v1` into native Preferences |

**The interface to satisfy** (`src/state/storeKitBridge.ts`) — reproduced so you can see the shape
without opening the file:

```ts
export interface SiliconStoreKitPlugin {
  getProduct(o: { productId: string }): Promise<NativeProduct & { available: boolean }>;
  getProducts(o: { productIds: string[] }): Promise<{ products: NativeProduct[] }>;
  purchase(o: { productId: string }): Promise<{ status: string; message?: string }>;
  restore(o: { productId?: string }): Promise<{ restored: boolean; owned?: string[] }>;
  isOwned(o: { productId: string }): Promise<{ owned: boolean }>;
  subscriptionStatus(o: { groupId: string }): Promise<NativeSubscriptionStatus>;
  manageSubscriptions(): Promise<{ shown: boolean }>;
  originalPurchase(): Promise<{ originalBuild?: number; originalVersion?: string }>;
  requestReview(): Promise<{ requested: boolean }>;
  addListener(e: "transactionUpdated", fn: (d: { productId: string }) => void): Promise<PluginListenerHandle>;
}
```

`NativeProduct` carries: `id`, `displayName`, `description`, `price` (**localized display string —
never format prices yourself**), `owned`, `kind`, `periodUnit`, `periodCount`, `introEligible`,
`introPeriod`, `groupId`.
`NativeSubscriptionStatus` carries: `active`, `productId`, `expiresAt`, `isTrial`, `willRenew`,
`inGracePeriod`.

`requestReview()` is **not** a purchase concern — it is the App Store rating prompt and must keep
working via the native plugin regardless of what happens to the purchase methods.

## 6. Phase plan

### ▸ Phase 0 — Feasibility spike **[HARD GATE — can cancel the project]**

**Do this before anything else. It is the only phase that can produce "don't do this at all".**

This app's iOS target is **SPM-only**. There is no `Podfile` and adding one is a significant,
invasive change to a working build. Capacitor 6's SPM support is newer than its CocoaPods support,
and not every third-party Capacitor plugin ships an SPM package.

**Determine, with evidence:**

1. Does the current `@revenuecat/purchases-capacitor` support **Capacitor 6** and **SPM**? Check the
   package's own `Package.swift` (does the npm package ship one?), its README, its changelog, and
   its issue tracker. Cite versions and links.
2. What is RevenueCat's iOS **minimum deployment target**? If it exceeds **15.0**, raising ours drops
   devices — quantify which, and flag it.
3. Does it require the **In-App Purchase capability** and any entitlement changes beyond what's
   already configured?
4. Does it pull transitive dependencies, and are those SPM-compatible?
5. What does it do to app size and cold-start time?

**Then answer the go/no-go question and present options:**

- **A — Official plugin, SPM.** Clean, if supported. Preferred.
- **B — Official plugin, requires CocoaPods.** Means introducing a `Podfile` to an SPM-only project,
  or running the hybrid setup. Materially more risk; quantify it honestly.
- **C — RevenueCat's iOS SDK direct, wrapped in the existing `SiliconStoreKit.swift` plugin.** Keeps
  the seam and the SPM setup (RevenueCat's native iOS SDK does support SPM), at the cost of writing
  the bridging ourselves. **This is often the best fit for this repo specifically** — the plugin and
  the interface already exist, so we'd be swapping the body of ~8 methods.
- **D — Don't migrate.** Direct StoreKit 2 already works, ships, and keeps "Data Not Collected".
  Name what RevenueCat buys that we actually need, and whether it is worth the privacy change.

**Deliverable:** a written recommendation with evidence and a rough effort estimate per option.
**Then STOP and wait for the user to choose.** Do not start Phase 1 on your own judgement.

### ▸ Phase 2 — The adapter *(the main code phase)*

**Write a RevenueCat adapter that satisfies `SiliconStoreKitPlugin`.** Do not rewrite the callers.

Suggested shape — adapt to whatever Phase 0 chose:

- New `src/state/revenueCatBridge.ts` implementing the same interface, translating RevenueCat's
  `CustomerInfo` / `EntitlementInfo` / offerings into `NativeProduct` and `NativeSubscriptionStatus`.
- `storeKitBridge.ts`'s `storeKit()` becomes the selector between implementations, behind a single
  flag, so the swap is revertible in one line.
- `proStore.ts` should need **minimal** change. If it needs a lot, the adapter is leaking.

Mapping work, all of which needs care:

| Interface concept | RevenueCat source | Trap |
|---|---|---|
| `active` | entitlement `pro` is active | RevenueCat treats grace period as active — good, matches us |
| `inGracePeriod` | billing-issue signal on the entitlement | Must stay distinct from plain expiry or `ProNudge` misfires |
| `isTrial` | entitlement period type = trial | Must be **per product row**, not the selected plan |
| `willRenew` | entitlement will-renew flag | Drives Settings copy |
| `expiresAt` | entitlement expiry | **Absent for lifetime.** Never treat "no date" as expired |
| `price` | package/product localized price string | **Never format prices yourself** — 3.1.2 exposure |
| `introEligible` | intro-eligibility API | Free-trial line must only show to eligible users |
| `owned` (lifetime) | non-subscription purchase in `CustomerInfo` | Identify lifetime by **identity**, not by missing expiry |
| `manageSubscriptions()` | `managementURL` | Must always have a fallback — a cancel path is a review requirement |
| `transactionUpdated` | customer-info update listener | Register **once**; two proxies double-deliver |

**Preserve exactly**, because each was a bug someone already fixed:

- The **offline-owned-product** path: an already-owned non-consumable tapped with no connection must
  resolve `purchased`, not `error`. Determine ownership from **local** data, never a network lookup
  that fails open.
- **Cancel is not an error.** Dismissing the sheet resolves `cancelled` with no banner. A cancel that
  shows an error is a documented 2.1.0 rejection.
- **Offline with an active subscription keeps Pro.** RevenueCat caches `CustomerInfo`; confirm the
  cache is actually consulted rather than the call failing closed.
- `syncPro()`'s revoke rule from invariant #4.
- The `NATIVE_PRO_WIRED` kill switch, and its companion: when it's false, the catalog must report
  unavailable so no dead buy button ships.

**Gate:** typecheck + full suite green; report exactly which files changed and which behaviours you
could not verify without a device.

### ▸ Phase 3 — Founding-owner grandfathering **[HIGHEST RISK]**

Everyone who bought the app at $8.99 keeps everything forever. Getting this wrong either **strips
paying customers** of what they own or **gives Pro away free** to everyone.

Today: `originalPurchase()` reads `AppTransaction.originalAppVersion` (the CFBundleVersion of the
original download), and `isFoundingBuild(n)` grants when `0 < n < FIRST_FREE_BUILD (5)`. Paid builds
were 1–4; build 5 is the first free one.

RevenueCat exposes an equivalent original-application-version on `CustomerInfo`. **Verify its exact
name, type, and semantics against current docs** — do not assume.

**The trap that is already fixed and must not regress:** in **sandbox and TestFlight**,
`originalAppVersion` reports **`"1.0"`** regardless of what was actually installed. Parsed, that is
build 1 — below `FIRST_FREE_BUILD` — so *every tester* reads as a paid-era owner, gets permanent free
Pro, and the paywall becomes untestable on exactly the builds it must be tested on. The current code
therefore only reports a build number when the receipt environment is **production**. RevenueCat's
value has the same underlying source and the same hazard.
**Determine how to detect sandbox through RevenueCat and keep the production-only guard.**

There is a pinned test for this — `"never grants founding from a version string alone"` in
`src/state/proStore.test.ts`. **It must still pass.** If your change makes it pass for the wrong
reason, that's a regression wearing a green check.

Also decide and document: for a user whose founding status was already granted and persisted locally,
does the RevenueCat path ever *revoke* it? The answer must be **no** — invariant #4.

**Gate:** report the mapping, the sandbox guard, and the migration story for already-granted users.

### ▸ Phase 4 — Existing-customer migration **[NO CUSTOMER MAY BE LOST]**

There are already live customers who purchased through direct StoreKit. Nothing about their
experience may change.

- Confirm the **restore** path recovers a subscription *and* a lifetime *and* the legacy Creative
  Mode unlock.
- Decide the **app user ID** strategy: anonymous IDs are the default and are correct for an app with

- Handle the transition window: a user who updates mid-subscription must not see a paywall for
  something they already pay for, even for one frame.
- Write the rollback: if this ships and entitlements break in the wild, what is the fastest patch?

**Gate:** a written migration story covering subscriber, lifetime owner, founding owner, legacy
Creative Mode owner, and brand-new free user.

### ▸ Phase 5 — Offerings-driven catalog *(optional; propose, don't assume)*

Driving the paywall from RevenueCat **Offerings** unlocks remote price changes and A/B experiments
with no app update — the main strategic reason to adopt RevenueCat at all.

But it also means the paywall's contents come from a server. **Guideline 3.1.2(c) requires** the
price, subscription length, and trial terms to be clearly disclosed at the point of purchase, so a
misconfigured remote offering becomes a compliance problem, not just a display bug.

If you build this: keep a **hardcoded local fallback** (the values in `pro.ts`) for when the offering
is unreachable, and never render a purchase button for a product whose price string is missing.

**Propose it at the gate. Do not build it as part of the migration.**

## 7. Traps, collected

Every one of these is either a bug that was already found and fixed here, or a documented App Store
rejection reason. Re-introducing one is a regression.

1. Sandbox `originalAppVersion == "1.0"` → free Pro for every tester. (Phase 3.)
2. Revoking an entitlement on a **partial** store read → logging out paying customers.
3. Treating a **missing expiry date** as expired → instantly killing every lifetime purchase.
4. Formatting prices in app code instead of using the store's localized string.
5. Showing the **selected** plan's trial terms on every row instead of each row's own.
6. A purchase **cancel** surfaced as an error banner. (Guideline 2.1.0.)
7. A buy button that cannot complete — e.g. catalog says available while purchase says unavailable.
   (Guideline 2.1.0; this exact bug shipped once here and was caught in review.)
8. A dead **Terms of Use** / **Privacy Policy** link in the purchase flow. (Guideline 3.1.2 — the
   most common rejection of all.)
9. Losing the **cancel path** — Manage Subscriptions must always resolve somewhere.
10. Registering the transaction listener twice → double-delivered purchases.
11. An entitlement check reaching `src/engine/` → determinism pin fails, or worse, doesn't.
12. Manufacturing urgency in copy — there is a test (`"never manufactures urgency"`) that fails the
    build on "limited time", "hurry", "act now" and friends. It exists on purpose.
13. Claiming a discount the store didn't give you. Real win-back pricing is configured server-side
    and rendered by the store's own sheet — never asserted in our UI.
14. Shipping a **secret** API key. Public SDK keys are fine; secret keys never enter the repo.
15. Hand-editing `CapApp-SPM/Package.swift` — regenerated by `npx cap sync ios`.

## 10. What NOT to do

- Do **not** start Phase 1+ before the user picks an option at the Phase 0 gate.
- Do **not** change prices, the free/Pro line, `FREE_TIER`, or what any tier includes. That is a
  product decision, not a migration step.
- Do **not** adopt RevenueCat's hosted Paywalls without an explicit decision — it conflicts with the
  one-purchase-surface rule and with this app's design system.
- Do **not** add analytics, attribution, or tracking SDKs alongside RevenueCat. The privacy change in
  Phase 6 is scoped to purchases and nothing else.
- Do **not** delete `src/state/iap.ts` or the legacy `com.wrexist.silicon.sandbox` product. People
  bought it.
- Do **not** claim native code works when you could not compile it.
- Do **not** leave the repo with a failing suite between sessions.
